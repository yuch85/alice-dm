Architecture Overview

This page describes what you need to build, not how we built ours. The system is agent-agnostic — any AI coding agent with tool-use capability can serve as the foundation. What matters is the infrastructure around it.

Core Components

1. Message Bridge

Required

Bidirectional adapter between your chat platform and the AI agent. Receives inbound messages, forwards them to the correct DM instance, and delivers DM responses back to the chat. Must handle media (images, audio, video) in both directions.

  • REST API for outbound sends (text, files, media)
  • Webhook or polling for inbound message capture
  • Message storage for history search and context
  • Support for group chats with sender identification

2. Campaign State Engine

Required

Persistent, structured storage for all campaign data. Flat files (JSON) work fine at typical campaign scale — version control is a feature, not a limitation. The state engine must support atomic mutations to prevent corruption during concurrent access.

  • Character data: HP, conditions, inventory, spell slots, abilities, equipment loadout
  • World data: NPCs, locations, factions, lore entries with discovery flags
  • Quest state: Active/completed quests, open threads, decision points
  • Knowledge tiers: Working memory → episode summaries → plot log → canon
  • Session metadata: Turn counter, scene state, combat tracker, last interaction timestamps

3. DM Agent Core

Required

The AI agent that serves as Game Master. Receives player messages, resolves actions against rules, mutates game state, and narrates outcomes. Must have access to: the current campaign state, the active ruleset, world data, and media generation tools.

  • Self-contained turn generation (narration + consequence + prompt in one response)
  • Dice rolling with auditable logs and modifier breakdowns
  • Ruleset-aware action resolution (not hardcoded to one system)
  • Fail-forward mechanics — bad rolls create complications, not dead ends
  • NPC voice consistency (one trait per NPC, word choice over accents)

4. Relay Router

Recommended

Required only for multi-campaign support. Routes inbound messages from different chat groups to the correct DM instance. Maintains a mapping of chat IDs to campaign sessions. Should support hot-reload of routing config without restart.

  • Chat ID → campaign → DM instance routing
  • Health endpoint for monitoring active routes
  • Owner dispatch endpoint for DM-to-campaign instructions
  • One-active-campaign-per-chat invariant enforcement

5. Campaign Hub (Player-Facing Web)

Recommended

A web page per campaign that players can bookmark. Renders campaign state into an interactive view: maps with clickable pins, character sheets, quest trackers. Must implement progressive reveal — players see only what they've discovered in-game.

  • Three core views: Map, Quests, Party
  • Character sheet with HP bar, spell slots, inventory, abilities
  • Level-up selection UI (spell/feature choices persist to state)
  • WebSocket connection to state server for live updates
  • Permanent URLs (assets must not expire)

6. State Server

Recommended

WebSocket server that bridges the campaign hub to campaign state. Handles player-initiated mutations (level-up choices, spell preparation, equipment changes) with role-based access control. DM sees everything; players see only unlocked entities.

  • Token-based authentication (short-lived player tokens, long-lived DM tokens)
  • Role-based view filtering on all reads
  • Rate limiting and connection limits
  • Universe merge (campaign data layers on top of shared universe data)

Media Generation Pipeline

Visual and audio generation makes campaigns immersive, but the system must work without it. All media is optional — the DM can run a pure-text campaign. When you do add media, here's what's needed:

Image Generation

Optional

Any image generation model works. The critical architectural decision is the anchor rule: the first image generated for any character or location becomes the canonical reference. All subsequent images of that subject must derive from the anchor (via image-to-image) to maintain visual consistency.

  • Text-to-image for initial portraits and establishing shots
  • Image-to-image for variations and scene-specific versions
  • Universe-level style prompt prepended to all generation requests
  • Per-campaign color theming

Video Generation

Optional

Two modes: ambient (silent footage seeded from a still) and dialogue (talking NPCs with synthesized speech). Video should be seeded from the character or location's anchor image for visual continuity. Subtitles should be hardcoded into all clips.

Voice Generation

Optional

Text-to-speech with zero-shot voice cloning for NPC consistency. Each character stores a voice reference. Post-processing presets (echo, radio static, underwater distortion) add atmosphere. Voice notes can be sent directly in chat or composited over video.

Collateral Manifest

Recommended

An asset index that tracks what's been generated: [subject_type][subject_id][asset_kind] → file_path. The DM checks this before generating anything new. Prevents duplicate generation, enforces the anchor rule, and enables batch pre-rendering.

State Architecture

Campaign state is the heart of the system. Get this right and everything else is tooling around it.

Knowledge Tiering

Required

Without knowledge tiering, the DM's context window fills up after a few sessions. The solution is a compression pipeline:

  • Tier 0 (Working): Raw turn-by-turn log of the current session
  • Tier 1 (Episodes): Compressed session summaries
  • Tier 2 (Plot Log): Major and critical events promoted from episode summaries
  • Tier 3 (Canon): Permanent facts — world changes that can never be forgotten

At session end, Tier 0 compresses into a Tier 1 episode. Important events promote upward. Old sessions drop out of active context but remain searchable.

Consolidation Pipeline

Required

Runs at session end (and optionally on inactivity auto-save). Compresses working memory, updates character state (HP, inventory, conditions), promotes events through knowledge tiers, increments session counter, and publishes a recap.

Progressive Reveal

Required

Every world entity (NPC, location, faction, lore) carries a visibility flag. The campaign hub and player-facing APIs filter on these flags. The DM sees everything; players see only what they've discovered. This is the core architectural constraint that enables the DM's vault.

Deprioritization

Recommended

Entities not interacted with for many sessions are excluded from the DM's active context (but remain in world data). Keeps the working set small even in campaigns with hundreds of NPCs and locations.

Mandate Mode Architecture

Mandate Mode is an async-play feature that lets players delegate their character to AI control. The architecture is straightforward:

Mandate Schema

Each character's state includes a mandate object:

  • active: Boolean — is this character under AI control?
  • persona: Freeform text describing how the character behaves ("fights dirty, retreats when outnumbered, always checks for exits")
  • escalation_triggers: List of conditions that pause auto-play and return control to the human player

The DM reads the persona and plays the character in-voice. When an escalation trigger fires, the DM narrates up to the decision point and waits for the human.

Ruleset System

Rulesets are reference documents, not code. The DM agent reads them the same way a human DM reads a rulebook. Adding a new game system means writing one reference document covering: core mechanics, action resolution, character progression, combat flow, and rest/recovery rules.

Resolution Hierarchy

The system checks for a ruleset at four levels: character → campaign → universe → global default. This allows mixed-system campaigns (a planar traveler using different mechanics) without special-case code.

Design Principles

These are the architectural decisions that shaped the system. They're opinionated — your build may choose differently — but they solve real problems we hit in production play.

Pre-render Nouns, Not Plots

Pre-generate NPC portraits, location maps, and ambient audio. Never pre-generate story beats or scripted sequences. Players diverge from expected paths constantly, and pre-scripted narrative is wasted work. Nouns are reusable; plots are not.

Immediate Write

When the DM improvises a new NPC or location, write it to world state immediately — don't defer to session-end consolidation. Deferred writes cause inconsistency when the DM references something that doesn't exist in state yet.

JSON Over Database

At campaign scale (hundreds of entities, not millions), version-controlled flat JSON with atomic CLI mutations beats a relational database. You get git history, easy backup, human-readable state, and no migration headaches. One writer per campaign eliminates concurrency issues.

Channel-Keyed Routing

One active campaign per chat group, not per player. A player can participate in multiple campaigns across different groups. The relay router maps chat IDs to campaigns, not user IDs to campaigns.

The Anchor Rule

The first visual generated for any character or location locks their appearance. All subsequent images derive from that anchor via image-to-image generation. This prevents the "NPC looks different every time" problem that plagues AI-generated campaigns.
